# First controlled execution experiment

This experiment runs original, fixed x86-64 machine instructions on the host CPU.
It is a native-execution probe, **not a CPU emulator, PS5 runner, or game boot**.
The original arithmetic fixtures are separate from loading; the new `loaded-elf`
fixture connects a generated ELF to the parser, loader, and checked guest-memory
API before execution. See [guest memory and loaded execution](guest-memory.md).
The worker command line accepts
fixture names, not filenames or arbitrary machine code. That interface defines
this experiment's scope, not a restriction on authorized local research.

## What actually executes

The host prepares four 64-bit numbers: `a`, `b`, `stored`, and `mask`.
Generated instructions perform this calculation:

```text
stored = ((a + b) * 3) modulo 2^64
return stored XOR mask
```

**Modulo 2^64** means retaining only the lowest 64 bits after arithmetic overflow.
**XOR** is bitwise exclusive OR: each result bit is one when the corresponding
input bits differ. Tests include zero, wraparound, high-bit cases, and 256
repeatable pseudo-random combinations, for 262 cases in total.

Instruction bytes are annotated in `experiments/native_probe.cpp`. A **register**
is a storage location inside the CPU. The fixture uses RCX for the data pointer
and RAX for arithmetic and its return value. A **calling convention** defines how
functions exchange arguments and results and which registers must be preserved.
Windows x64 receives our pointer in RCX; Linux x86-64 System V receives it in RDI,
so the Linux fixture moves RDI to RCX first. Neither adapter is a PS5 ABI bridge.
The fixtures make no further calls or stack allocations.

**Native execution** means the host CPU directly executes these instructions,
without an interpreter translating each operation. A similar instruction set does
not provide console libraries, operating-system services, or graphics interfaces.

## Memory and process boundary

Separate code and data allocations each have an accessible middle page surrounded
by inaccessible pages. A **page** is a unit of virtual memory protection; its size
is queried from the host. The surrounding **guard pages** make accesses there
fault instead of silently accessing adjacent memory.

The code page starts readable/writable, receives the bytes, and becomes
readable/executable. It is never deliberately writable and executable at once:
a **W^X** policy (write XOR execute). The worker synchronizes the instruction
cache using the host interface. The data page stays writable and non-executable.

A Python supervisor starts a new worker process for each fixture. A deliberate
worker crash does not terminate the supervisor. This is fault containment for a
test, **not a security sandbox**: workers retain their normal host privileges.
The probe does not spawn further descendants.

Four fixtures deliberately execute invalid `UD2`, write to executable code,
read a guard page, and fetch instructions from a non-executable page. The
supervisor requires a ready message before checking the exact expected Windows
exception exit status or Linux signal. Arbitrary nonzero exits do not pass.
Linux core dumps are disabled and Windows error dialogs are suppressed.

An infinite-loop fixture tests timeout handling. Python terminates and waits for
that direct child before reporting the timeout. A fresh arithmetic worker then
verifies that testing can continue. Use the supervisor for fault/loop fixtures.

## Expected results and limitations

C++ checks returned RAX and compares the entire writable page with expected
bytes, including unchanged inputs and surrounding sentinel bytes. It also checks
that fixture bytes remain unchanged. Python independently recomputes every
reported arithmetic case with arbitrary-precision integers and 64-bit wrapping.

This does not check every register, flag, stack condition, exception context, or
memory-ordering behavior. There is no recovery inside a faulted worker, guest
thread scheduling, or translated code. Only Clang's function-type metadata check
is suppressed at the raw-code call boundary: generated bytes have no compiler
function-type metadata. Other compiled host checks remain enabled. ASan signal
interception is disabled in worker environments for deliberate faults. Generated
instructions themselves are not instrumented by ASan or UBSan.

Calling generated code through a function pointer relies on the host/compiler
ABI, not portable ISO C++. Supported targets are Windows MSVC x64 and Linux
x86-64. Other targets must use `-DPS5RT_NATIVE_PROBE=OFF` for inspection-only
builds. Forbidden executable mappings cause failure, not a passing skipped test.

## Run it

After building normally:

```powershell
ctest --test-dir build -C Debug -R native_probe -V
```

For just the successful worker:

```powershell
.\build\Debug\ps5rt_native_probe.exe arithmetic
```

Passing does not enable executing an arbitrary ELF input. The generated ELF path
uses an explicit host leaf-function contract, not platform process startup.
Guest stack/startup and platform ABI support remain to be implemented before
claiming that a supplied binary runs.
